# Release procedure

Audience: the maintainer and an agent assisting them. Building candidates and
checking versions are read-only preparation. Creating/pushing a release tag
and publishing a release each need explicit human authorization. Adopting the
repository or asking for a build does not authorize either action.

## 1. Prepare a reviewed release commit

1. Work in the actual `Telefonorosso/openvpn` checkout or its contributor fork.
   Read `AGENTS.md`; verify the repository root, origin URL and working-tree
   status. Preserve other work and use a release-preparation PR.
2. Read `VERSION`. For another port revision of the same OpenVPN version,
   increment only the positive `-amiga.N` revision. For an upstream update,
   follow `UPSTREAM.md` and reset the port revision to 1. Do not change upstream
   `version.m4` just to bump the Amiga port. The driver ABI version is separate.
3. Update `CHANGELOG.md` with actual changes and limitations. Use the approved
   release date when converting an unreleased entry. No invented test claims.
4. Run the tested entrypoint and inspect its candidate:

   ```sh
   python3 tools/build.py
   ```

   It does not tag, push, install or publish. Verify the current version's ZIP
   and tar.gz against `build/packages/SHA256SUMS`. An unverified archive or dirty
   source marker is not a verified release source; use a clean reviewed commit
   and its successful CI candidate.
5. Open/review the preparation PR. Require all five public jobs at its final
   head and affected native results. Merge with authorization, preserving the
   import/subtree history. Wait for the main-branch build and inspect its
   source identity, packages, versions, notices and installation layout again.

For a checksum check, use `sha256sum -c SHA256SUMS` on Linux or
`shasum -a 256 -c SHA256SUMS` on macOS from the candidate directory. Both archive
formats have the same installed payload. Follow `INSTALL.md`; candidate
creation itself is not an Amiga installation or a full provider qualification.

## 2. Record the exact tag proposal (no tag creation yet)

In a clean, current main checkout whose origin is the authoritative repository:

```sh
git status --short
git remote -v
git rev-parse HEAD
python3 tools/check-version.py
```

Record the full commit, desired `v` + `VERSION` tag, successful CI run URLs,
native coverage (including each SHA), package hashes and release notes in the
proposal. `git status --short` must be empty. Ensure the proposed tag does not
already exist; never move or overwrite an existing release tag.

The assisting agent can derive/check the proposed tag without creating it:

```sh
release_tag="v$(python3 tools/check-version.py)"
python3 tools/check-version.py --tag "$release_tag"
git ls-remote --tags origin "refs/tags/$release_tag" "refs/tags/$release_tag^{}"
```

The last command must return no existing tag references. The maintainer must
approve this specific version and commit before proceeding.

## 3. After explicit tag authorization

An authorized agent can create/push the annotated tag at the approved commit.
Recheck `HEAD` still equals the approved full SHA and the source is clean before
running these write commands:

```sh
git tag -a "$release_tag" -m "AmiOpenVPN $release_tag" HEAD
git push origin "refs/tags/$release_tag"
```

These are release actions, not commands to run while evaluating the handoff.
Pushing the tag starts CI. GitHub's Code > Download ZIP is not this release
process. Do not use an alternate release form to create/publish a tag before
checks complete, and do not duplicate the draft generated by the workflow.

## 4. Verify the tagged candidate and draft

In Actions, open the **Build and test** run for that exact pushed tag. Require
version checks, both host jobs, cross/volamos, Copperline/Roadshow and **Prepare
draft release on version tags** to succeed. Queued/cancelled/skipped tests are
not passes. The tag-release job creates a draft with the freshly built archives,
checksums and provenance; it does not publish it.

Verify the remote annotated tag resolves to the approved SHA. Verify the tagged
run's `SOURCE_COMMIT` and clean `source-provenance.json`, both archive checksums,
matching package payloads, and expected `bin/`, `Devs/Networks/`, `stacks/` and
notices. Confirm the actual client/device binary hashes agree with the
interoperability evidence being cited. Do not label a different tree/SHA or
older native run as exact-tag evidence.

For Miami-affecting runtime changes, have the authorized private operator run
**Build and test** with `miami_native=true` against that same reviewed tag.
The CLI form, after the documented runner/variables are configured, is:

```sh
gh workflow run ci.yml --repo Telefonorosso/openvpn --ref "$release_tag" -f miami_native=true
```

The operator verifies the run head equals the approved commit before starting
an ephemeral runner. Require actual Miami return 0, two encrypted cycles and
route/DNS restoration. The private job is normally skipped on the tag-push run;
that skip is not a native result. For unchanged runtime, document the separate
baseline SHA and the exact unchanged-core comparison, with the maintainer's
accepted validation scope. Never silently reuse old native evidence.

If any gate fails, investigate on a new fix/preparation commit. Do not force an
old tag forward or bypass tests. Agree a fresh version/tag with the maintainer
when required.

## 5. Human publication and cleanup

Open Releases and edit the **existing draft** for the approved tag. Replace its
brief generated notes with the reviewed changelog, tested stacks, exact
coverage/limits, requirements and installation link. Keep the package assets,
checksums and provenance together; do not substitute a local or older build.

After the maintainer explicitly approves publication, they or an authorized
agent can publish that draft. Release tag creation and publication are distinct
approvals. Without publication approval, leave the verified draft unpublished.
No release is created or published by preparing this handoff.

Retain compact source/run/hash evidence. Remove only task-created scratch and
finished branches, preserve original licensed assets and pending work, and
remove any ephemeral runner after its job. Keep related issues open unless
closure of each issue was explicitly approved.
